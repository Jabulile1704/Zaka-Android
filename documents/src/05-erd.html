1. The schema

2. Why there are no relationships

An entity relationship diagram with no relationships looks like an oversight. It is the central decision of this schema.

A category is a text key, not a row in a lookup table. The category column holds "groceries", and the sixteen permitted values live in a Kotlin enumeration. The obvious alternative — a categories table with a foreign key — was rejected for three reasons.

  • Nothing would ever be written to it. The categories are fixed at build time. A lookup table would be read-only data shipped in a migration, which is a Kotlin enumeration with extra steps.
  • A join on every read, for nothing. Every list, every chart and every export would join to recover a label that the application already knows.
  • It would not survive renaming. The real risk here is not referential integrity, it is a refactor: rename a category in code and, if the column held an ordinal or an enum name, every saved record would silently come to mean something else. A stable text key cannot be renamed by accident, because the compiler never touches it.

That last point is not hypothetical. On the iOS original the category list was replaced and later partly restored, and because the column held text, the affected expenses returned to their original categories on their own — nothing had overwritten them.

2.1 How integrity is kept instead

Normally enforced byHere
A foreign key constraintA total function on read. An unrecognised category becomes other; an unrecognised symbology becomes code128. Reading a row can never fail.
A migration that rewrites rows when a reference changesA mapping applied at read time. A retired key is translated for display and left untouched in the database, so the decision is reversible.
Constraints on value rangesValidation in the form: an amount must be greater than zero before it can be saved.
Reading never writes

This is asserted by test: store a record with a retired category, read it back through the mapping, and confirm the stored key is still the retired one. It is what makes the mapping a display convenience rather than a silent migration.

3.3 Why dates are integers

Epoch milliseconds sort correctly in SQL, need no type converter, and let the month query be WHERE date >= ? AND date < ?, which the index on date can serve. An ISO-8601 string would also sort correctly and would cost four times the space for no gain.

The range is half-open on purpose. A month runs from local midnight on the first up to, but not including, local midnight on the first of the next month, so nobody has to reason about whether the last millisecond of a month is included. Both ends are computed in the device's zone: in South Africa a month begins two hours before the UTC date changes, and taking that boundary in UTC would put the first evening of each month in the wrong one.

4. From table to application

The tables are not the types the application reasons about. Each row is mapped to a domain record, and the mapping is where the keys become values.

TableDomain recordWhat changes in the mapping
expensescore.Expensecategory text → ExpenseCategory, via the retired-key mapping. date millis → an instant.
loyalty_cardscore.LoyaltyCardsymbology text → BarcodeSymbology, falling back where unknown. added_at millis → an instant. The last four digits are derived, never stored.

Keeping the two apart costs a mapper and buys the thing above: the column stays a string whatever happens to the Kotlin.

5. Schema versioning

The schema is at version 1 and no migrations exist. Room's schema export is deliberately switched off until there is a migration to validate against — an exported schema that nobody has committed looks like a record without being one. The first migration turns it on.

What the storage does not do

The database is unencrypted SQLite in the app's private directory. It is protected by the device lock and by Android's app sandbox, and by nothing else. That is appropriate for expense records and shop card numbers, and it is the reason a payment card number must never be stored here.
