1. Summary

93 automated tests run on every push and every pull request. All pass. They cover the arithmetic, the database, the state holders and the semantics a screen reader is given. They cover nothing about how the app looks, and that is the headline finding of this report.

Material qualification

No build in this report has run on a developer machine. The machine the code was written on has no JDK, no Gradle and no Android SDK, so continuous integration is the only thing that has ever compiled it, and the only thing that has ever run these tests. The application has not been launched by a human. A green pipeline here says the project assembles and the arithmetic is right. It says nothing about whether the theme works, whether the chart is readable, or whether a barcode scans.

2.1 Approach

  • The iOS suite is the specification. Tests were translated from the Swift originals before the Kotlin they test was written, so the port had something to satisfy rather than a reference to paraphrase.
  • Nothing is mocked. Store tests run the real Room database in memory; state-holder tests drive real view models over that database. A fake repository would only prove the fake behaves like the fake.
  • The barcode encoder is checked against an independent decoder written inside the test, so a mistake shared between encoder and expectation cannot pass.
  • Clocks and time zones are injected, so behaviour at a month boundary and over midnight is asserted rather than reasoned about.

4. Defect log

Every defect found so far, how it was found, and where it stands. Four were found and fixed; the rest are known and scheduled.

IDDefectFound bySeverityState
DEF-1 App would not compile against the declared SDK. Compose 1.13 requires consumers to compile against API 37.1; the project declared 37, which means 37.0. The build failed at checkDebugAarMetadata with six identical complaints. CI, first runMajorfixed
DEF-2 Month-to-date total frozen at launch. The current month was read once where the state flow was declared, so the figure above the tab bar kept totalling the month in which the process started. Leaving the app open overnight on the first of a month showed last month's total above this month's expenses. Day headings went stale the same way, so "Today" meant yesterday. Code reviewMajorfixed
DEF-3 Double tap on Save recorded two expenses. Nothing guarded the in-flight save, so two presses launched two writes, both reading an unsaved record and both inserting. Easy to trigger: the button sits under the thumb with the keypad open. Code reviewMajorfixed
DEF-4 Test suite would not compile. An assertion helper was imported as a top-level function when it is a member, so the accessibility suite failed to build. CIMinorfixed
DEF-5 A deletion cannot be undone. One swipe removes an expense with no confirmation and no way back. Restricting the swipe to one direction reduces mis-swipes; it is not a substitute for undo. Code reviewMajoropen
DEF-6 A state holder is retained for every expense ever edited. The edit screen keys its view model on the expense id, so each one edited stays in the activity's store until the process dies — the pattern the add screen deliberately avoided. Code reviewMinoropen
DEF-7 The list query reads the whole table. Every insert re-emits, re-maps and re-groups every expense ever recorded. Acceptable for a year of data; it wants a windowed or paged query before it is several years old. Code reviewMinoropen
DEF-8 A number formatter is constructed on every call. Once per row, per heading, per legend entry, per recomposition — the hottest path the app has. Code reviewTrivialopen
DEF-9 A save reports success for an update that changed nothing. The row count returned by the update is discarded, so saving an expense that was deleted elsewhere silently does nothing and the caller is told it worked. Code reviewMinoropen
DEF-10 A future-dated expense inflates the daily rate. The divisor is the days elapsed, but nothing stops an expense being dated later in the month, so the money lands in the total while the divisor stays small. Code reviewTrivialopen
DEF-11 The accessibility action is rebuilt on every recomposition, invalidating the semantics node with it, on a list that re-emits whenever any expense changes. Code reviewTrivialopen

Two observations that are not defects but were raised in review and are worth recording: parameter names shadowing flow properties in the insights state holder, and validation of the amount living in two places with no single source of truth.

The useful lesson

Reading the diff as a whole found three real functional defects that 93 passing tests did not. Two are now regression-tested. A test suite says whether the code does what its author thought; it cannot say whether the author thought of everything.

6. Conclusion

The arithmetic, the storage and the state of this application are well covered and all of it passes. The three functional defects found so far were found by reading the code, not by running it, and the two that mattered are now held closed by tests.

The honest state of quality is therefore: correct as far as anything has been able to check, and unexercised as software. The next meaningful quality activity is not another test — it is launching the app.
